# 技术博客：CAN 分布式伺服全系统联调——从字节层链路到双电机同步闭环

> 项目：基于 CAN 总线的分布式伺服控制系统　阶段五-5.3：全系统联调
> 平台：STM32F103C8T6 Blue Pill ×2（主站=板C/从站=板B）、SN65HVD230 ×2、JGA25-370 电机+霍尔编码器 ×2、TB6612 ×2、250kbps、IWDG 1s
> 状态：✅ 全部通过——主站 CAN 下发目标、从站 PID 闭环跟随、反馈回报、OLED 双板同屏、故障注入自愈、看门狗浸泡

---

## 1. 为什么 5.3 才是"分布式"真正成立的时刻

阶段三把**字节层链路**打通了：主站发一帧 `0x101`，从站收到闪灯并回一帧 `0x201`。但那时从站**没有电机、没有编码器**——链路两端传输的只是"测试数据"，没有任何业务含义。

5.3 做的事情只有一件：**让链路两端开始运载真实业务**。

```
阶段三（字节层）  CAN 帧 = 测试载荷          → "链路通"
5.3（应用层）     CAN 帧 = 目标位置/编码器反馈 → "系统会干活"
```

最终验证的是这样一句话：**"主站说 500，两块板子的电机都转到 500，主站的屏幕同时显示两块板子的位置。"**——一句话里同时含下行（目标下发）、闭环（从站跟随）、上行（反馈回报）、人机界面（OLED 同屏），这才是分布式伺服控制系统作为"一个系统"的完整闭环。

## 2. 系统架构：双电机双板分布式伺服

### 2.1 硬件拓扑

```
                     ┌─────────────── 120Ω ──────── CANH ────────── 120Ω ───────────────┐
                     │                                                                      │
        ┌────────────┴──────┐                                            ┌────────────┴──────┐
        │ 板C  主站 NODE=0   │                                            │ 板B  从站 NODE=1   │
        │                    │── SN65HVD230 ── CANL ──────────────────────│                    │
        │  PB8=RX  PB9=TX    │                       GND（共地）          │  PB8=RX  PB9=TX    │
        │                    │                                            │                    │
        │  PA0/PA1 编码器#1  │                                            │  PA0/PA1 编码器#2  │
        │  PA6/PA7/PB1 →TB6612#1 → 电机#1                                  │  PA6/PA7/PB1 →TB6612#2 → 电机#2  │
        │  PB6/PB7  OLED     │                                            │                    │
        └────────────────────┘                                            └────────────────────┘
               逻辑供电 USB-C        两个 TB6612 VM 各自独立 5V 源            逻辑供电 USB-C
```

三块板（A/B/C）中板 A 的 CAN 接收路径在阶段三确诊为克隆芯片物理报废，**退居单机演示板**；5.3 由板 C（主站，带电机#1+OLED）和板 B（从站，新加电机#2+编码器）组成双节点系统。这也是分布式系统故障处理的真实一环：**节点不健康就把它摘掉，剩下两节点继续工作。**

### 2.2 数据流（一个完整的业务周期）

```
主站串口: pos 500
   │
   ▼
主站 CANTask (每 100ms): 0x101  [target=500, flags bit0=enable]
   │                                          
   ▼                          ▼
从站 RX 回调: g_target_position = 500    主站 RX 回调: g_slave_pos = 从站编码器值
   │
   ▼
从站 ControlTask (PID 闭环): 驱动电机#2 收敛到 500
   │
   ▼
从站 CANTask (每 100ms): 0x201  [enc=499, status bit0=stall]
   │
   ▼
主站 OLED:  M-POS 499 / S-POS 500 / CAN OK <count>
```

**闭环的边界要分清楚**：从站的 PID 闭环（编码器→控制量）是**本地环**，不经过 CAN；CAN 运载的是"目标下发 + 反馈回报"的**位置级信息**。这是分布式伺服与单机伺服的本质区别——**CAN 上流动的不是控制量，是目标/状态**。CAN 周期 100ms，而本地环是 ms 级，两者解耦，CAN 的延迟不影响本地环的稳定性。

### 2.3 软件分工（与阶段三对比）

| 角色 | 阶段三（字节层）| 5.3（应用层）|
|---|---|---|
| 主站 CANTask | 发 `0x101` 测试载荷、数反馈 | 发 `0x101` 目标+flags；接收 `0x201` **锁存从站位置/堵转** |
| 从站 CANTask | 收到 `0x101` 闪灯、回 `0x201` | 收到 `0x101` **驱动 g_target_position**；回 `0x201` **带编码器+堵转状态** |
| 主站 DisplayTask | 第六行 `CAN OK <count>` | 升级为 **M-POS/M-TGT/M-SPD/M-PWM/S-POS** 双板布局 |
| 从站 ControlTask | 无（裸板）| **PID 位置闭环 + 堵转保护** |

两端的角色都从"收发测试帧"变成了"运载真实业务"——代码增量不大（主站锁存从站反馈、从站闭环），但系统的含义完全不同。

## 3. 分布式里的"目标所有权"：命令为什么发给主站 ★

这是 5.3 联调中第一个被误读的现象。**从站串口发 `pos -200`，目标只闪一拍就被盖回 200**——看起来像"从站不听话"。

**解读：这是设计行为。** 从站的目标值由 `0x101` 帧驱动，主站每 100ms 广播一次它的目标（默认 200）。所以从站的本地串口命令只能活一拍（下一次 CAN 帧到来就覆盖）。

```
分布式系统的"目标所有权"：
  单机系统: 目标来自本地（串口/按键/代码）
  分布式系统: 从站目标永远来自主站 CAN，本地命令只是单机调试口
```

这带来的调试习惯是决定性的：**要驱动从站电机，命令必须发给主站**。从站的目标是"只读"的，由总线决定。很多分布式联调卡在"为什么命令没生效"，本质是没想清楚目标的唯一来源。

> 面试展开：把"目标所有权"讲成**控制权边界**的设计决策——从站不持有自己的目标，就永远不会和主站"打架"。这是主从式（master-slave）分布式架构的纪律：**单一控制源，防止多主竞争**。将来要加"从站本地手动模式"，就在协议里加一个 mode 标志位，让主站决定从站处于"总线跟随"还是"本地控制"。

## 4. 从站：PID 闭环 + 堵转保护（两个本地环）

从站的本地控制环在 5.3 前单机版已存在，5.3 只把它接上 CAN 目标源。两个环节值得展开：

### 4.1 PID 位置闭环

```
每 ~1ms（ControlTask）:
  error  = g_target_position - g_enc
  g_target_speed = Kp*error  （位置误差 → 速度指令）
  g_pwm  = PID(g_target_speed - g_speed)  （速度误差 → 占空比）
  按正负设置 PA7/PB1 方向 + PA6 输出 PWM
```

两级串联（位置外环 → 速度内环），位置误差大时全速逼近，接近时减速收敛。从站 CSV 里能看到标准收敛形态：`enc 209 → 499` 逐渐逼近、稳定后 `0,500,0,0,0`（误差 0、速度 0、pwm 0）。

### 4.2 堵转保护（踩坑重灾区，见坑 20）

```
DiagTask（每 50ms）:
  if (g_pwm != 0 && g_speed > -2 && g_speed < 2)   // 有输出但速度≈0
      stall_cnt++                                  // 连续 ~1s
      if (stall_cnt ≥ 20) g_stall = 1
ControlTask:
  if (g_stall) { g_target_speed=0; g_integral=0; g_pwm=0; }   // 杀停
```

**堵转保护把"电机卡死"翻译成了"编码器没动"**——它的判据是编码器速度。这条链路的第一个环节就是编码器：编码器不读数，保护逻辑看到的是"一直没动"，于是把"电机全速空转"误判成"堵转"杀掉。**这就是"假堵转"的机制**（坑 20 详见踩坑笔记）。

## 5. 主站 OLED：从"单机显示"到"双板同屏"

阶段三的 OLED 只显示本板状态，5.3 升级为**主站显示整个系统的状态**。数据来源是 `0x201` 反馈帧：

```c
// 主站 RX 回调（0x201 精确过滤，收到的每一帧都是从站反馈）:
g_slave_pos   = (int16_t)(rx_data[0] | (rx_data[1] << 8));  // 从站编码器位置
g_slave_stall = rx_data[2] & 0x01;                          // 从站堵转状态
```

DisplayTask 布局：

```
M-POS  499        ← 本板（主站）编码器位置
M-TGT  500        ← 本板目标
M-SPD    0        ← 本板速度
M-PWM    0        ← 本板占空比
S-POS  500        ← 从站位置（来自 0x201）★
CAN OK 12345      ← 链路计数（5s 不涨转 --）
```

验收画面：**M-POS 和 S-POS 同步跟随主站目标**——一眼确认下行（从站跟随）和上行（反馈回来）两条链路都活着。第 5 行在从站堵转时变成 `STALL`，把从站的故障在 100ms 内搬到主站屏幕。

> 面试展开：显示层是分布式系统的**诊断面**。单机系统自己显示自己，分布式系统需要**中央显示**——主站成了"系统观察窗"。反馈链路通了之后，"显示从站状态"只是把数据取出来的问题，这就是分层设计的好处。

## 6. 排障实战：5.3 的三个真问题

### 6.1 从站编码器恒 0：先排硬件，别先怀疑代码 ★

从站电机能转但 `enc` 列恒 0 → 位置环全速追 → "先转很多后不转"（假堵转）。

**关键动作**：在怀疑代码前，把从站固件的编码器路径和**已知正常的主站固件逐字节对照**——初始化、MspInit 引脚配置、启动调用、无重映射。**两边完全相同**。同一份代码一块板读数、一块板恒 0 → **差异必在硬件**。

硬件排查按概率：
1. **测编码器供电**（蓝↔黑 ~3.3V）——插头错位、没落上是最常见的
2. **测 A/B 信号**（转电机看绿/黄对黑翻转）
3. **换编码器对照**（把好板的编码器插到故障板）

> 教训：**"代码是不是错了"要用对照实验回答，而不是猜**。物理变量差异 > 代码变量差异时，先排硬件。这也是阶段三"同固件板 B 好板 A 坏 = 硅片问题"方法论的重演——**对照实验在硬件排障里是万能的**。

### 6.2 主站"能往前不能往后"：反向脚接触不良的症状特征

主站 `pos 1000` 超调到 1054，反向 PWM 一路加到 -48，编码器纹丝不动 → 堵转锁死。**正向完全正常，反向调不回来**。

TB6612 反向驱动 = AIN1=L、AIN2=H。**若 AIN2（PB1）悬空/接触不良**：正向靠 AIN1=H 还能转（AIN2 浮空读低，正好是 L），反向要 AIN2=H 却拉不起来 → "能往前不能往后"。重新接线后消失。

> 教训：**位置环超调修正依赖反向驱动**。"往回调不动"不是 PID 问题，是方向驱动硬件问题。验证：从高位 `pos 0`，走不回来就是反向断了。

### 6.3 CAN 链路全死：加 OLED 时动了 CAN 的邻居

联调中 `CAN DBG rx= 15 tx= 18` 两个计数器**同时冻结**。tx 冻结 = 帧没人 ACK（邮箱一直重传）、rx 冻结 = 收不到反馈 → **从站不在总线上**。

诱因：给板 C 加 OLED 时，**OLED 在 PB6/PB7、CAN 在 PB8/PB9，引脚只差两格**，跳线碰/挤了收发器排线。重新理线后 `rx=tx 160→200→220` 同步增长——完美链路恢复。

> 教训：**加新硬件时检查引脚邻接**。软件可观测性的价值在这里体现：`rx=tx 冻结`（从站掉线）和 `时通时断`（接触不良）和 `复位循环`（芯片硬故障）三个指纹一眼可辨，不用拆线猜。

### 6.4 CAN 清堵转：协议预留位让运维不靠断电

从站的堵转锁存原本只能靠本地串口 `pos` 或断电解除。演示时从站一堵转就死锁，体验极差。阶段三协议里预留的 **flags bit1（清堵转）** 这时用上了：

```
主站: 串口收 "pos xxx" → g_clr_stall_cnt = 10
      后续 10 帧（~1s）的 0x101 里 flags |= 0x02
从站: RX 回调 if (rx_data[2] & 0x02) g_stall = 0;   // 远程解锁
```

验证：捏住从站电机 → OLED `S-POS` 变 `STALL` → 松手主站发 `pos 500` → 从站自动解锁恢复，**免断电免拔线**。

> 面试展开：这是"协议设计与运维通道"的实例。阶段三设计协议时**宁可多留不用，不要用到再扩**——bit1 预留了半年，5.3 才用上。扩容时帧结构一字未改，只多解释一个 bit，上位机零改动。**协议的可扩展性在真正需要时才被证明。**
