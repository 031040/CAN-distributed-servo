# 技术博客：CAN 双板通信字节层联调——从双板闪灯到链路自愈

> 项目：基于 CAN 总线的分布式伺服控制系统　阶段三：双板字节层联调
> 平台：STM32F103C8T6 Blue Pill ×2（主站/从站）、SN65HVD230 CAN 收发器 ×2、250kbps
> 状态：✅ 链路打通（双向收发 + 故障注入自愈 + 看门狗浸泡通过）

---

## 1. 为什么先做"字节层"联调

分布式系统做第一步通信时，最容易犯的错是直接上应用层业务（PID 下发、状态同步），结果"业务不工作"时根本分不清是**物理链路**的问题还是**业务逻辑**的问题。所以本项目把联调严格分层：

```
物理层（接线/终端/位时序） → 字节层（一帧能收能发） → 应用层（业务协议）
```

阶段三只做**字节层**：主站发一帧 `0x101`，从站收到闪灯并回一帧 `0x201`，主站收到闪灯——**链路活没活，用眼睛看就知道**。业务（目标下发、反馈回报、伺服协作）全部留到 5.3，不混进来。

**可观测性设计贯穿始终**：每一步都有"看得见的结果"作为判据，不做黑盒联调。

## 2. 硬件：总线接线与位时序

### 2.1 网络拓扑

```
┌─────────────┐   CANH ────┬──── 120Ω   120Ω ────┬──── CANH   ┌─────────────┐
│ 板C 主站    │            │      ┌──────┐        │            │ 板B 从站    │
│ PB8=RX PB9=TX│──SN65HVD230┴──────┤ 总线  ├──────┴──SN65HVD230─│ PB8=RX PB9=TX│
└─────────────┘   CANL ────────────┴──────┴───────────── CANL  └─────────────┘
                     GND ───────────────────────────── GND（共地）
```

- **收发器**：SN65HVD230，3.3V 器件，**VCC 必须从板子取 3V3**（RXD/TXD/3V3/GND 四根）。它把 MCU 的 CAN_TX/CAN_RX 单端信号转成 CANH/CANL 差分信号。
- **终端电阻**：**总线两端各一个 120Ω**（CANH↔CANL 轨道间），匹配总线特征阻抗吸收反射。两端节点标准做法。
- **共地**：两板 GND 直连。CAN 虽然是差分，但参考地必须通，否则共模范围超限会丢帧。
- **引脚**：CAN1 **重映射到 PB8=RX / PB9=TX**（`__HAL_AFIO_REMAP_CAN1_2()`），主从站一致。

### 2.2 位时序：为什么是 250kbps

本项目时钟是 **HSI 8MHz 直驱**（无 PLL/HSE），APB1=8MHz → CAN 时钟 = 8MHz。

| 参数 | 值 | 含义 |
|---|---|---|
| Prescaler | 4 | 总线时钟 8MHz/4 = 2MHz |
| 位时间 | 2MHz / 250kbps = **8 TQ** | 1 位分成 8 个时间量子 |
| Sync | 1 TQ | 同步段 |
| BS1 | 5 TQ | 传播段 + 相位段1 |
| BS2 | 2 TQ | 相位段2 |
| SJW | 1 TQ | 重同步跳变宽度 |
| **采样点** | (1+5)/8 = **75%** | 在 BS1 末尾采样 |

**为什么 8 TQ 是 HSI 下的极限**：8 TQ/bit 意味着 BS1+BS2 = 6 TQ，再降就只剩同步段和相位段了，采样点裕量和抗干扰都吃紧；而想要更高波特率（如 500k），位时间只剩 4 TQ，不满足"BS1≥2、BS2≥2"的规范约束。加上 HSI ±2% 容差，250k 是 HSI 直驱下可靠性的上限。**面试要能说出"为什么 250k 而不是 500k"**——这不是拍脑袋选的，是时钟树约束下的推导。

## 3. 应用层协议：极简且可扩展

```
11-bit 标准帧：
  0x100 + node_id   主站 → 节点：目标位置
                      data[0:1] = int16 LE 目标位置
                      data[2]   = flags（bit0=使能, bit1=清堵转）
  0x200 + node_id   节点 → 主站：反馈
                      data[0:1] = int16 LE 编码器位置
                      data[2]   = status（bit0=堵转）
  node_id：0=主站，1/2=从站（预留三节点）   DLC=3（紧凑）
```

设计要点：
- **ID 即寻址**：`0x100+id` / `0x200+id` 用标准帧 ID 编码角色和节点号，接收侧不用解析数据就能按 ID 分流——**过滤器直接在硬件层过滤**，不匹配的帧根本进不了 FIFO。
- **数据紧凑**：2 字节位置 + 1 字节标志，DLC=3。伺服控制里位置值 int16 够用，能省则省。
- **小端序**：`data[0]=低字节, data[1]=高字节`，跨端平台（STM32 LE 小端）天然一致，不需字节序转换。
- **非阻塞发送 + 自动重传**：`HAL_CAN_AddTxMessage` 只入邮箱不等待；有终端电阻的前提下 `AutoRetransmission=ENABLE`，帧发不出去就自动重传直到被 ACK——这是链路自愈的软件基础。

## 4. 软件：HAL CAN 全流程与过滤器掩码语义（重点）

### 4.1 初始化流程

```c
MX_CAN_Init();                  // 250kbps, Normal, AutoRetransmission=ENABLE, AutoBusOff=ENABLE

// USER CODE 2：
HAL_NVIC_SetPriority(CAN1_RX0_IRQn, 5, 0);   // >= configMAX_SYSCALL_INTERRUPT_PRIORITY，ISR 才可用 FromISR
HAL_NVIC_EnableIRQ(CAN1_RX0_IRQn);

CAN_FilterTypeDef f = {0};
f.FilterBank = 0;               // bank 0
f.FilterMode = CAN_FILTERMODE_IDMASK;        // 掩码模式
f.FilterScale = CAN_FILTERSCALE_32BIT;
f.FilterFIFOAssignment = CAN_FILTER_FIFO0;
f.FilterActivation = CAN_FILTER_ENABLE;      // {0} 初始化默认 DISABLE → 过滤器不激活 = 收不到帧（经典坑）
f.FilterIdHigh = (uint16_t)(((0x200 + 1) << 5) & 0xFFFF);  // 目标帧 0x201
f.FilterIdLow = 0;
f.FilterMaskIdHigh = 0; f.FilterMaskIdLow = 0;  // mask=0：见 4.2
HAL_CAN_ConfigFilter(&hcan, &f);

HAL_CAN_Start(&hcan);
HAL_CAN_ActivateNotification(&hcan, CAN_IT_RX_FIFO0_MSG_PENDING);

// 中断回调（ISR 上下文，尽量短）：
void HAL_CAN_RxFifo0MsgPendingCallback(CAN_HandleTypeDef *hcanp)
{
    static CAN_RxHeaderTypeDef hdr; static uint8_t data[8];
    if (HAL_CAN_GetRxMessage(hcanp, CAN_RX_FIFO0, &hdr, data) != HAL_OK) return;
    g_can_rx_cnt++;                 // 计数器：链路健康度的主指标
    HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_13);   // 每帧闪灯 = 裸板可观测性
}
```

注意几个点：
- **过滤器激活位**：`CAN_FilterTypeDef f = {0}` 会把 `FilterActivation` 初始化为 DISABLE，忘了设 ENABLE 过滤器就是死的——这是"配置全对但收不到帧"的头号原因。
- **中断优先级 5**：`>= configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`，保证回调里能安全用 `xSemaphoreGiveFromISR` 这类 FromISR API（FreeRTOS 的边界要求）。
- **ISR 里只计数/闪灯**，帧解析放任务里——ISR 越短越好。

### 4.2 过滤器掩码语义：STM32 与 GD32 的"坑反" ★

这是本阶段最有价值的硬件知识点。**同一套寄存器偏移，STM32 和 GD32 的掩码位语义是相反的**：

| 芯片 | 掩码位 1 | 掩码位 0 | 全收配置 | 精确匹配配置 |
|---|---|---|---|---|
| **STM32 F1** | 不关心（don't care） | 必须匹配 | `0xFFFFFFFF` | `0x00000000` |
| **GD32** | 必须匹配 | 不关心 | `0x00000000` | `0xFFFFFFFF` |

**危险场景**：按 STM32 习惯给主站配"全收"（掩码 `0xFFFFFFFF`），如果实际芯片是 GD32 语义，就反转为"精确匹配 ID=0"——**把从站的反馈帧全拒了**。一块好板会被误判成坏板，浪费一整轮排障。

**双兼容解法（本项目的选择）**：对要收的目标帧用 **mask=0 + 过滤器 ID=目标帧**：
- STM32 语义：mask=0 = 所有位必须匹配 = **只收目标帧** ✓
- GD32 语义：mask=0 = 所有位不关心 = **全收（含目标帧）** ✓

两种硅片下**目标帧一定放行**。所以主站和从站都用"精确 ID + mask=0"，从站收 `0x101`、主站收 `0x201`，**不用知道板子的真实厂商语义也能一次调通**。代价是主站将来要多从站时要加过滤器 bank（收 `0x202` 就再配一个 bank），这是可接受的扩展成本。

> 面试展开：可以把"掩码语义反向"作为"跨厂商外设兼容"的实例讲——配置外设时不能想当然用某个厂商的语义，要在关键路径上选"两种语义交集"的安全配置。

## 5. 可观测性设计：让链路状态"看得见"

通信联调最大的敌人是"没现象"。本项目设计了四级观测通道，从粗到细：

| 通道 | 内容 | 粒度 |
|---|---|---|
| **双板 LED** | 主/从站 PC13 每收一帧闪一下 | 链路"活没活"一眼可见 |
| **串口 DBG** | 主站每 2s 打 `CAN DBG rx=… tx=…` | 计数级：rx 涨=收到反馈、tx 涨=帧被 ACK |
| **OLED** | 主站第六行 `CAN OK <count>`，计数 5s 不涨转 `--` | 人机界面（板子带 OLED 时） |
| **计数器** | `g_can_rx_cnt`/`g_can_tx_cnt` | 程序内判据，接故障告警 |

设计原则：
- **自诊断的输出通道不能依赖被诊断部件本身**（延续 OLED 阶段的教训）：OLED 可能坏，串口可能没接，**LED + 串口自由文本**是两条互相独立的通道。
- **串口协议一字不改**：所有新增调试行（横幅、DBG）都是**自由文本行**（无逗号、不足 5 段），上位机解析 `if len(parts) < 5: continue` 直接跳过——**上位机零改动**。这是给成熟协议"打补丁式"加可观测性的安全缝。
- **裸板主判据是 LED**：板 B 没有 OLED 也没有串口，"收没收到"就靠 PC13 每帧一闪。没有这个，联调就是瞎调。

## 6. 排障实战：克隆芯片的判别方法论

阶段三排障遇到真问题：主站（板A）**发送正常但永远收不到帧**。6 版固件配置（HAL 过滤器 / 无过滤器 / GD32 直写 / 裸排空 / 关中断 / 只读 RF0R）全部失败。以下方法把问题从"软件"一步步锁定到"硅片"：

### 6.1 对照实验（最重要）

**同一份干净 HAL 固件，烧到板 B（从站）一切正常**（收帧闪灯、自动 ACK），烧到板 A 收不到任何帧。软件栈完全一样，唯一变量是硬件 → **问题在板 A 的硅片，不在软件**。这是最快的定性手段，没有对照实验就容易被"是不是配置没写对"反复拉回软件层。

### 6.2 时序指纹：破译复位周期

板 A 上加了"读 FIFO 邮箱寄存器取数据"的代码后，**每 ~3.3s 复位一次**。把周期拆成已知时基：

```
3.3s ≈ 2s（DBG 打印周期，CANTask 第 20 拍）+ 1s（IWDG 超时）+ 0.3s（启动初始化）
```

复位发生的位置 = DBG 读邮箱的那一刻。**周期时长不是随机数，是系统时基的线性组合**——把周期拆开，就能反推卡死点。而且 CSV "正常流 2s → 停 1s → 复位"的相位关系也吻合，三条线索互证。

### 6.3 最小干预证伪

"会不会是 CAN 中断风暴拖死系统？"——直接把 IER 写 0 关掉所有 CAN 中断，复位依旧 → **证伪中断假设，收敛到"访问地址本身"**。一个假设用最小干预排除，别在错误方向耗时间。

### 6.4 寄存器回读照妖镜

对疑似克隆的芯片，判断外设真实性看**整组寄存器能否 round-trip**：
- 过滤器寄存器（0x200~0x244）：同一份写代码，两次启动一次读到"生效值"、一次读到**垃圾值**——读写不稳定。
- `FR2@0x244` 每一次运行**恒读 `0x22377E`**，写什么都不理——只读固定内容。
- `IER` 写 2 读回 `0x40750B`、写 0 读回 `0x783800`——**写不进去**。
- `hcan.State`（RAM 变量）读到 255——连软件句柄状态都异常。

多个独立坏点同时指向同一外设 = **外设本体问题**，不是配置问题。

### 6.5 决定性证据：读 FIFO 邮箱触发总线错误

CAN 收帧的**必要环节**是读 FIFO 邮箱（0x1B0 段）拿数据。这颗克隆**没有实现邮箱寄存器**——一访问就触发**总线错误 → HardFault → IWDG 复位**。把这个环节在代码里删掉，复位立即消失（对照实验）。**接收的必要环节物理缺失 = 接收不可能实现**，这就是判死刑的根因。

### 6.6 芯片身份验证

`DBGMCU->IDCODE @ 0xE0042000` 读 **0**（正品 F103 应读 `0x410` 之类），丝印却是"STM32F103C8T6"——**假 ID + 假丝印**。虽然 ID 可以被仿（部分克隆会伪装 0x410），但配合寄存器回读和对照实验，结论就实锤了。

### 6.7 结论与决策

**板 A 的 CAN 接收物理报废，任何角色都不行**（主站要收反馈、从站要收目标，都要 RX）。发送路径正常（TX 计数一直涨，对端在 ACK）——这颗芯片的 CAN 只实现了一半。板 A 的电机/编码器/串口/OLED 全正常，仍是完整单机伺服板，退居单节点演示，不浪费。**该换板就换板**，不在死路上耗迭代。

## 7. 换板验证与故障注入（链路自愈演示）

换第三块蓝丸（板C）当主站，板 B 保持从站，重建干净主站固件后组网：

**验证过程**：
1. **双 LED**：板 C 收 `0x201` 闪、板 B 收 `0x101` 闪，两块都均匀快闪 = **双向链路成立**。
2. **故障注入**：拔掉一根总线线 → 双板停闪（通信断）；板 B 的从站固件 5s 后**快闪 5 下报警**（"没人 ACK 我的帧"）；**插回 → 自动重传恢复，双板重新均匀闪**——链路自愈演示成功。
3. **看门狗浸泡**：5 分钟连续运行，复位一次没有，IWDG 全过。

故障注入是这套系统最直观的演示：**拔线 → 停 → 插线 → 自己恢复**，把 CAN 的自动重传机制变成了可讲给面试官的故事。
