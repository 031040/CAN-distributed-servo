# 调试踩坑笔记：OLED 贪吃蛇 + 编码器旋钮（V10_Snake）

> 时间：2026-08-16　板卡：STM32F103C8T6（Blue Pill）　显示：SSD1306 0.96" 128×64 OLED（I2C 4 针模块，复用 V8_OLED）　输入：JGA25-370 电机编码器（TIM2 硬件编码器模式，PA0/PA1）　工具链：Keil MDK 5.23（ARMCC 5.06）+ CubeMX 6.17
> 对应工程：`E:\Desktop\CAN\Project\V10_Snake`（由 V8_OLED 复制而来，**V8 保持原样可烧录**）
> 定位：简历"大一大二早期项目"——与大四 CAN 项目形成成长弧线（大二把编码器当旋钮输入做界面，大四把编码器用到电机测速闭环）

## 0. 一句话背景

基于 V8_OLED（FreeRTOS 4 任务 + OLED + 编码器 + PID/电机）复制出 V10_Snake：**保留 FreeRTOS 骨架和 OLED/编码器外设，删掉电机/PID/串口上位机协议，把 4 个任务改成贪吃蛇任务组**。编码器旋钮控制蛇转向，OLED 画 16×7 棋盘 + 分数条，串口打游戏事件日志。零新料，纯软件。

**为什么选这个项目**：面试讲"编码器"时，大二项目是"编码器 → 游戏方向输入"，大四项目是"编码器 → 电机测速闭环"。同一个外设，从输入到控制，成长线一句话讲清。

---

## A. 设计期就确定的坑（提前规避）

### 坑 1：贪吃蛇不需要 FreeRTOS，但**保留** FreeRTOS 是刻意的工程决策

- **纠结**：贪吃蛇逻辑本质是单循环（读旋钮 + 步进 + 画），裸机也能写。V8_OLED 是 FreeRTOS 4 任务工程，要不要把 RTOS 拆掉改成裸机？
- **决策**：**保留 FreeRTOS**。理由分两层：
  1. **工程风险最低**：拆 RTOS 要动 CubeMX `.ioc`、`stm32f1xx_it.c`（SysTick/PendSV handler）、时基（TIM4→SysTick）、`FreeRTOSConfig.h`、Keil 工程组，任何一环出错都可能让"能跑的 V8"变成"跑不起来的 V10"。保留骨架 = 只改 USER CODE 区 = 每步可回退。
  2. **复用现有任务分工**：V8 的"Control 算 / Comm 传 / Diag 喂 / Display 画"正好映射到贪吃蛇的"状态机算 / 事件日志 / 心跳喂狗 / 棋盘绘制"，**换内容不换骨架**。
- **教训**：**"简单需求"不一定要"简化架构"**。当已有架构能承载新需求、且改动面最小时，保留它是更稳的选择。面试讲清"为什么这个项目还用了 RTOS"，反而是主动的设计思考。

### 坑 2：HAL 时基在 TIM4、SysTick 归 FreeRTOS——任务外裸调 HAL_Delay 是雷区

- **事实**：V8 把 SysTick 给了 FreeRTOS（1ms 节拍），HAL 的 `HAL_InitTick` 被 CubeMX 重定向到 **TIM4**（见 `stm32f1xx_hal_timebase_tim.c` + main.c 的 `HAL_TIM_PeriodElapsedCallback`）。
- **风险**：在**任务外**（如 main 里调度器启动前）调用 `HAL_Delay`，它的内部 `uwTick` 来自 TIM4 中断，此时调度器没跑、TIM4 中断照常工作 → 实际可用。但**在任务里**如果长时间 `HAL_Delay`（比如想"等蛇走一步"），会占死该任务、拖慢其他任务节拍。
- **解决**：**前进节拍一律用 tick 计数差**（`xTaskGetTickCount()` 差 ≥ `g_speed_ms` 才走一步），不用任何 Delay。这样 20ms 任务里同时做"读旋钮"+"判方向"+"判断是否该步进"，互不阻塞。
- **教训**：**RTOS 项目里"时间"有两个来源**（HAL 的 uwTick vs RTOS 的 tick），用混了会出"看起来一样的延时"却行为不同的问题。节拍类逻辑统一走 RTOS tick。

### 坑 3：编码器旋钮的方向判断——用计数差分，别用 EXTI 中断

- **设计**：V8 已把 PA0/PA1 配成 **TIM2 硬件编码器模式（TI12）**，`HAL_TIM_Encoder_Start` 后读 `__HAL_TIM_GET_COUNTER` 即得 4 倍频计数。贪吃蛇直接复用，**零新外设配置**。
- **为什么不用 EXTI**：EXTI 要新配 PA0/PA1 中断 + NVIC 优先级 + 判 A/B 相位，改动面大且和"复用 V8"冲突。编码器模式读差分天然能判方向：
  ```c
  int16_t delta = (int16_t)__HAL_TIM_GET_COUNTER(&htim2) - prev_enc;
  prev_enc = cur;
  if (delta >= TURN_THRESH)      // 顺时针 -> 右转
  else if (delta <= -TURN_THRESH) // 逆时针 -> 左转
  ```
- **注意 int16 回绕**：计数器是 16 位有符号，手动转轴速度下差值不会爆掉，但代码用 `int16_t` 减 `int16_t`，编译器自动处理正负回绕（`0x7FFF → 0x8000` 的减法仍是正确的小正/负差）。
- **教训**：**改需求时优先找"现成外设能不能复用"**。编码器本来就是为测位置/速度设计的，当旋钮用是"降级使用"，配置零成本。

### 坑 4：转向要防抖——单次转动会持续输出一串脉冲

- **现象（预判）**：手动转一下电机轴，编码器不是输出"1 个脉冲"就停，而是**一串脉冲**（JGA25-370 齿轮箱转动手感 + 4 倍频）。如果每次采样 delta≥阈值就转向，转一下会连续转 3~4 次方向。
- **解决**：**转向锁存**：
  ```c
  if ((delta >= TURN_THRESH || delta <= -TURN_THRESH) &&
      (xTaskGetTickCount() - last_turn) >= TURN_LOCK_MS)   // 200ms 锁存
  { 转向; last_turn = xTaskGetTickCount(); }
  ```
  转一下只认一次方向，200ms 内再转无效；连续快速转（转轴持续转）则每 200ms 转一次，节奏可控。
- **教训**：**机械输入的"一按"和"电信号的一串"不是一回事**。任何旋钮/按键/开关输入进软件都要过一层防抖，这是嵌入式的基本功，面试可展开。

### 坑 5：蛇身是数组移位——检查边界和"尾巴要不要查"

- **设计**：`g_snake[0]` 是蛇头，`g_snake[g_snake_len-1]` 是尾巴。步进 = 头插入 + 尾丢弃：
  ```c
  for (uint8_t i = g_snake_len; i > 0; i--) g_snake[i] = g_snake[i-1];  // 整体后移
  g_snake[0] = 新头;
  ```
- **两个细节**：
  1. **边界**：蛇最长 `SNAKE_MAX = GRID_W*GRID_H = 112`。移位会写 `g_snake[g_snake_len]`，当 `len == SNAKE_MAX` 时越界 1。加保护：`if (g_snake_len >= SNAKE_MAX) { GAME_OVER; return; }`（满格=胜利=结束）。
  2. **撞自己时尾巴要不要查**：如果这一步**没吃到食物**，尾巴这步会移走，新头可以合法进入尾巴原位置（经典贪吃蛇允许"追尾"）；如果**吃到食物**，尾巴保留，新头必须查全部身体。代码里 `body = eat ? g_snake_len : g_snake_len - 1`。
- **教训**：**"数组移位模拟身体移动"是对的方向，但边界（越界/尾巴语义）是 90% 的 bug 来源**。

### 坑 6：食物生成要避免"死在蛇身上"——伪随机 + 冲突重试

- **设计**：`spawn_food()` 用 FreeRTOS tick（`xTaskGetTickCount`）当熵源，LCG（`seed*1103515245u+12345u`）生成伪随机坐标，**循环重试直到落在空格**（`food_on_snake()` 检查），兜底扫全盘找第一个空格。
- **为什么用 LCG 不用 `rand()`**：`rand()` 要接 `srand()`，且标准库随机质量对这种场景够但引入依赖；LCG 3 行实现、确定性、好讲（面试问"伪随机怎么做的"）。
- **教训**：**"随机生成"在嵌入式里 = 种子 + 确定性算法 + 约束检查**。落到已有对象上（蛇身）必须重试，否则游戏会出现"食物和蛇重叠"的怪象。

### 坑 7：分数行和棋盘分层——顶部 8px 是分数条，棋盘 16×7 格

- **布局**：OLED 128×64，用 **8×8 像素格** → 全屏是 16 列 × 8 行。但**顶部一行（page 0）给分数条**，棋盘用下方 **16 列 × 7 行**（`GRID_W=16, GRID_H=7`）。
- **画格**：`draw_cell(gx, gy)` 把格坐标映射到像素：`x0 = gx*8+1, y0 = 8+gy*8+1`，画 6×6 实心方块（**留 1px 边距**，格子和格子之间有空隙，棋盘清晰可读）。
- **食物 vs 蛇身区分**：蛇身画 6×6 实心，食物画 8×8 实心（大一格），一眼能分辨。
- **教训**：**像素屏的"网格坐标系"是游戏 UI 的地基**。格子怎么映射、边距留不留、食物怎么区分于蛇，这些"看起来小"的决策决定游戏好不好看、好不好讲。

### 坑 8：绘制走脏页刷新——全量重绘用 OLED_Clear + 只 Flush 变化的页

- **设计**：DisplayTask 每 100ms（10Hz）`OLED_Clear()` 清帧缓冲 → 重画分数 + 蛇 + 食物 → `OLED_Flush()`。驱动的 `OLED_Flush` 只推 `dirty_mask` 里标记的页，**变化的页才走 I2C**。
- **为什么够快**：脏页机制 + 全量重绘，I2C 实际每帧只推 1~4 页（分数页 + 蛇占的页 + 食物页），远小于"8 页全刷"。10Hz 刷新对贪吃蛇（最低 60ms/步）绰绰有余。
- **注意**：OLED_Clear 会标脏全部 8 页，但代码是先 `OLED_Clear` 再画再 `Flush`——`Flush` 才真正走 I2C，所以"清"只是内存操作（1KB memset），**I2C 流量由 Flush 控制**。这个先例来自 V8（脏页 + 局部重绘）。
- **教训**：**"清屏"和"刷屏"要分开想**：清屏是内存写（快），刷屏是外设 IO（慢）。用脏页机制把慢的部分控制在"变了才推"，UI 才跟得上游戏节奏。

## B. 编译/验证踩到的坑

> 说明：本次工程是"复制 + 改造"，编译用 Keil 命令行批处理（见坑 9）；**上板验证按"先插后上电 + 一次只验证一个新模块"铁律**，IWDG 在，调试靠串口日志/看现象，不用断点。

### 坑 9：Keil 命令行编译——`Start-Process -Wait` 才有退出码

- **现象**：PowerShell 里直接 `& UV4.exe -b xxx.uvprojx` 返回后 `$LASTEXITCODE` 是空、编译日志也拿不到——因为 **UV4 是 GUI 子系统程序**，`&` 调用立即返回不等待。
- **解决**：
  ```powershell
  $p = Start-Process "D:\MDK5\UV4\UV4.exe" -ArgumentList @('-r','"xxx.uvprojx"','-j0','-o','"build_log.txt"') -Wait -PassThru -NoNewWindow
  $p.ExitCode   # 0=成功 1=警告 2+=错误
  ```
  `-r` 强制重建（`-b` 可能因为文件时间戳而跳过重编），`-o` 指定日志文件。
- **教训**：**命令行自动化 GUI 工具要查"它是不是 GUI 程序"**。UV4 的退出码语义：0 无错无警、1 有警告、>1 有错误——CI 脚本可以拿这个做门禁。

### 坑 10：主程序"能编译"不等于"游戏逻辑对"——上板前先在代码层面自查

- **现象（自查）**：第一次写完 `snake_step`，逻辑上有两个隐患：满格越界、追尾撞自己。编译都通过，但跑起来会是"莫名 Game Over / 内存写坏"。
- **处理**：不是等上板踩雷，而是**写完就逐分支检查**：
  - 边界：`g_snake_len >= SNAKE_MAX` 保护（坑 5）
  - 撞自己：`body = eat ? len : len-1`（尾巴语义，坑 5）
  - 食物：落在蛇身重试（坑 6）
  - 转向：200ms 锁存防抖（坑 4）
  - 步进节拍：tick 计数差，非阻塞（坑 2）
- **教训**：**游戏逻辑是纯内存操作，不用上板也能静态走查**。把"跑起来才暴露"的 bug 在代码层面先过一遍，上板就是验证不是排雷。

### 坑 11：GAME_OVER 后"转动旋钮重新开始"——用同一把编码器做双用途

- **设计**：游戏进行中旋钮转向；GAME_OVER 后旋钮转向变成"重新开始"。同一个 `delta` 判断，两个状态两种语义：
  ```c
  if (g_state == 1) { if (|delta| >= THRESH) { snake_init(); log; } continue; }
  // 否则才处理转向
  ```
- **细节**：GAME_OVER 分支必须 `continue`，避免"刚重启又触发一次转向"串台。`snake_init()` 里重置蛇/分数/速度/状态并重新生成食物。
- **教训**：**同一个输入源在状态机里可以有多个含义**——这正是状态机的价值。面试问"游戏状态机怎么设计"就讲这一段。

### 坑 12：串口日志是"游戏状态机"的可观测性出口

- **设计**：CommTask 每 100ms 检测状态变化：分数涨了 → 打 `[Snake] eat score=N len=N speed=Nms`；状态变 Game Over → 打 `[Snake] game over`；重启 → `[Snake] restart`。启动横幅：`OLED: OK` + `Snake Start. Rotate motor shaft: CW = turn right, CCW = turn left`。
- **为什么**：贪吃蛇纯靠眼睛看 OLED 也行，但**串口日志让状态机行为可验证、可回放**（分数递增节奏、死亡原因、重启事件），面试还能讲"用日志验证状态机"。这是 V8 的"可观测性设计"思想延续到游戏项目。
- **教训**：**任何逻辑都要有"不看屏幕也知道它对不对"的通道**。对游戏，串口日志就是那个通道。

## C. 一句话总结

贪吃蛇项目的坑分三层：**架构决策**（保留 RTOS 而非裸机、复用 TIM2 编码器模式而非新配 EXTI）、**时序设计**（tick 计数节拍、转向锁存防抖、脏页刷新）、**游戏逻辑本身**（数组移位边界、追尾语义、食物冲突重试、状态机双用途旋钮）。最值得记住的一条：**"简单项目"不等于"随手写"**——状态机、防抖、边界检查、可观测性这些基本功全在，只是比大四项目少了一层分布式硬件。这正好是简历里"从简单到复杂"的叙事基础。
