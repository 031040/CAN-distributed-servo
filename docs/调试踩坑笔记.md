# 调试踩坑笔记：CAN 双板通信字节层联调（V9_CAN）+ 5.3 全系统联调

> 时间：2026-08-10 ~ 08-15　板卡：STM32F103C8T6 Blue Pill ×3（板A/板B/板C）　收发器：SN65HVD230 ×2　工具链：Keil MDK + CubeMX 6.17
> 对应工程：`Project\V9_CAN`（板A主站，克隆排障版，已废弃）、`Project\V9_CAN - 副本`（板B从站，干净可用）、`Project\V9_CAN_master`（板C主站，干净可用，本阶段最终固件）
> 前置：V8_OLED 四任务系统跑通（串口协议一字未改）。阶段三目标 = **CAN 字节层链路打通**：主站发 `0x101` 目标帧 → 从站收到闪灯回 `0x201` 反馈帧 → 主站收到闪灯。
> 结论：**链路已打通**（板C主站 ↔ 板B从站，双向收发 + 故障注入自愈 + 看门狗浸泡全过）。**板A 的 CAN 接收判死刑**——非正品克隆硅片缺陷，任何软件配置收不到帧，板A 退居单机电机板。

---

## 0. 一句话背景

给"单机伺服 + OLED + 上位机"的 V8 系统加上 CAN 通信，让两块蓝丸在 250kbps 的总线上做字节层双向通信（主站下发目标位置、从站回报编码器反馈），为最终三节点分布式伺服协作铺路。**排障主线的故事是：板A 这颗"STM32F103C8T6"是克隆，它的 CAN 只实现了发送、接收路径根本没接对——花了 6 版固件、约 5 次串口排障迭代才把它彻底定性，然后换板一次通过。**

## A. 设计期就确定的坑（提前规避，每个都是"不规避必炸"级别）

### 坑 1：250kbps 是 HSI 8MHz 直驱下的极限选择

- **背景**：本项目时钟铁律是 HSI 8MHz 直驱（无 PLL/HSE，PCLK1=8MHz），CAN 时钟 = PCLK1 = 8MHz。
- **位时序推导**：CAN 位时间 = 1 + BS1 + BS2（TQ）。250kbps → 位时间 = 8MHz/250k = **32 TQ**，但 8MHz 下 32 TQ 意味着 BS1+BS2=31 TQ（超出 F1 寄存器上限，BS1≤16TQ/BS2≤8TQ）。
- **实际配置**：Prescaler=4 → 总线时钟 2MHz → 250kbps 需要位时间 = 2MHz/250k = **8 TQ**。BS1=5TQ、BS2=2TQ、SJW=1TQ → 8 TQ/bit，采样点 (1+5)/8 = **75%**。这是 V6_CAN_loopback 实测成立的组合。
- **教训**：**HSI 直驱下 CAN 只有 8 TQ/bit**（250k 是极限），别贪 500k/1M——HSI ±2% 容差在更高速率下采样点裕量吃紧，且 8 TQ 是同步段以外能塞下的最少 TQ 组合。面试讲清"为什么 250k 而不是 500k"是加分项。

### 坑 2：无终端电阻 = 总线反射 = CRC/ACK 错误

- **现象（V6 时代已踩）**：板子单独连收发器、总线另一端悬空时，帧发不出去/重传失败。
- **原因**：CAN 是差分总线，两端节点必须各挂一个 **120Ω 终端电阻**（匹配总线特征阻抗 ~120Ω）吸收反射；没有终端，信号在开路端反射回来，产生误码/ACK 丢。
- **解决**：A 侧、B 侧各一个 120Ω（CANH↔CANL 轨道间），两端节点标准做法。**有终端了自动重传才安全，`AutoRetransmission = ENABLE` 要开回**（V6 因无终端关过）。
- **特别注意**：**板 A 单独上电、总线另一端没设备时，帧发不出去是预期行为**——没有对端 ACK，邮箱一直重传。这不是故障，接上板 B 就有响应。排障时别把它当 bug。

### 坑 3：收发器必须从板子取 3V3——USB 不供 3.3

- **事实**：SN65HVD230 是 3.3V 器件，**VCC 必须接板子的 3V3 引脚**（RXD/TXD/3V3/GND 四根）。它不靠 USB，漏了 VCC 总线根本没有信号。
- **USB 相关的都不需要单独接 3.3**（用户反复问，记档）：
  - USB-C 给蓝丸供电：不用接 3.3，板载 AMS1117 从 5V 自己转出 3.3。
  - CH340 串口：只接 TX/RX/GND 三根，**别把 CH340 模块的 3.3V 输出并到板子的 3.3V**（两个稳压器输出打架）。
  - ST-Link 的 3V3 线只是**目标电压检测 VTREF**，不是供电；能连就不用接，Keil 报 "cannot connect / target voltage" 就补上。
- **教训**：接线先分清"这个器件从哪取电"。5V 电源轨 ≠ 3.3V 逻辑轨，别混。

### 坑 4：共地 + 先插后上电（延续铁律）

- 板 A/B、两块收发器、TB6612、电源模块、编码器、CH340 的 **GND 全部要通**（共地是 CAN 正常工作的前提，差分信号也要参考地）。
- **先插后上电**：所有线接好再上电，上电后再动线容易烧模块。
- MB-102 面包板电源模块**不可靠**，先万用表测 5V 再上电；板子供电用 USB Type-C。
- TB6612 STBY 必须接 3.3V 电机才转；VM=5V 电机电、VCC=3.3V 逻辑电。

### 坑 5：从站裸板必须用 PC13 闪灯做接收指示

- **背景**：板 B 是裸板，没有 OLED 也没有串口。"它到底收没收到主站的帧"不可见，排障就瞎。
- **解决**：用板载 **PC13 LED 每收到一帧 0x101 闪一下** 作为接收指示。上电先 3 次短闪（自检：新固件在跑 + LED 接线好），之后每帧一 toggle。
- **主站同样**：板 C 主站也加了收帧闪 PC13（V9_CAN_master），裸板不接串口也能看接收。**两块板都闪 = 双向链路成立**，这是本阶段最主要的判据。
- **教训**：**没有观测手段的通信联调 = 盲调**。在裸板上先给"有没有收到"装个眼睛，再谈别的。

### 坑 6：串口协议一字不改——DBG/横幅走自由文本行

- **背景**：上位机 `main_plot.py` 解析 5 值 CSV（enc,pos,speed,tspeed,pwm），**协议一个字都不能动**，否则上位机全挂。
- **解决**：所有新增的调试输出（开机横幅 `CAN: OK`、周期 `CAN DBG rx=… tx=…`）都是**自由文本行**（无逗号、不足 5 段），上位机第 75 行 `if len(parts) < 5: continue` 直接跳过。**上位机零改动**。
- **教训**：联调期要加可观测性，但不能动协议——"自由文本行"是协议扩展的安全缝。延续 OLED 阶段坑 13 的做法。

### 坑 7：过滤器掩码语义 STM32 与 GD32 相反——mask=0 是双兼容的保险做法 ★

- **STM32 F1 语义**：掩码位 **1 = 不关心，0 = 必须匹配**。全收 = 掩码全 1 = `0xFFFFFFFF`；精确匹配 = 掩码全 0。
- **GD32 语义（反转）**：掩码位 **1 = 必须匹配，0 = 不关心**。全收 = 掩码全 0 = `0x00000000`。
- **为什么危险**：如果主站按 STM32 习惯配"全收"（掩码 0xFFFFFFFF），而实际芯片是 GD32 语义，那就反转为"精确匹配 ID=0"——**把 0x201 反馈帧全拒了**。一块好板会被误判成坏板。
- **双兼容解法**：对要收的**目标帧**用 **mask=0 + 过滤器 ID=目标帧**：
  - STM32 语义：mask=0 = 全位必须匹配 = **只收目标帧** ✓
  - GD32 语义：mask=0 = 全位不关心 = **全收（含目标帧）** ✓
  - **两种硅片下目标帧都放行**，不会误判。从站（收 0x101）一直就是这么配的，板 B 上验证正常。
- **本阶段应用**：主站过滤器从原设计"全收"改成"精确匹配 `0x200+1`=0x201、mask=0"（V9_CAN_master）。三节点时再加一个过滤器 bank 收 0x202。
- **教训**：**过滤器配置是"语义相关"的**，跨厂商芯片语义可能反转。在"要确保某帧一定进来"的场景，mask=0 + 精确 ID 是两种语义下的安全交集。

### 坑 8：IWDG 断点调试冲突（延续阶段四）

- IWDG 1s 超时激活，Keil 断点一停 1s 后硬件复位。**所有验证靠打印/观察现象闭环，不用断点**。
- 这次排障尤其依赖"烧录 → 看串口 DBG → 改 → 再烧"的迭代，DBG 行就是眼睛。

## B. 本次实际踩到的坑（板A 克隆排查主线，全过程的料都在这）

### 坑 9：读 CAN FIFO 邮箱（0x1B0）在板A 上触发总线错误 → HardFault → IWDG 复位 ★★（决定性缺陷）

- **现象**：给主站固件加上"读 FIFO 邮箱寄存器（RIR/RDLR，0x1B0+）取帧数据"的裸排空逻辑后，板A **每 ~3.3s 复位一次**（串口横幅反复重打），CSV 正常流一阵后停 ~1s 再复位。
- **排查经过**：把邮箱读取从 DBG 和裸排空里**全部删掉，只保留"读 RF0R 看 FMP 位 + 置 RFOM0 释放"**后——**复位消失，板子连续跑 15 秒+不复位**。对照实验实锤：复位源就是"访问 0x1B0 段寄存器"。
- **原因**：这颗克隆芯片的 CAN **没有实现 FIFO 邮箱寄存器**。访问 0x1B0 段触发**总线错误** → HardFault_Handler 死循环 → 卡死 → IWDG 1s 超时硬件复位。CAN 收帧的**必要环节**就是读邮箱取数据，这一环物理缺失 = **接收不可能实现**。
- **教训**：**对照实验是最快的定性工具**——"删掉某段代码故障消失"就是那段代码的问题，不用猜。这也是后面敢判板A死刑的关键一步。

### 坑 10：~3.3s 复位周期的破译——复位间隔本身就是指纹 ★

- **数据**：横幅重打间隔实测 3.294s（42.034→45.328→48.622→51.916）。
- **破译**：DBG 行在 CANTask 第 20 拍（100ms 节拍 × 20 = **2s**）读 0x1B0 → 当场总线错误卡死 → **IWDG 1s** 后复位 → 再经过 **~0.3s** 启动/初始化到横幅 → 横幅间隔 ≈ 2 + 1 + 0.3 = **3.3s**。三条线索全对上（DBG 间隔 2s + IWDG 1s + 启动 0.3s）。
- **且**：14:35/14:39 两版固件 CSV 都是"正常流 ~2s → 停 ~1s → 复位"，停的瞬间正好是 DBG 触发读邮箱的时刻——CSV 停止点与复位周期的相位关系也吻合。
- **教训**：**复位/卡死周期的时长不是随机数，是系统里各个时基的线性组合**（本案例 = 调试周期 + 看门狗超时 + 启动时间）。把周期拆成已知时基的和，就能反推卡死发生在哪个环节——这是嵌入式排障里的"时序指纹"思维。

### 坑 11：ISR 风暴假设被证伪——关中断（IER=0）仍复位

- **假设**：会不会是 CAN 中断风暴（ISR 疯狂重入）把系统拖死/喂不上狗？
- **验证**：把 CAN 的 IER 直接写 0，**所有 CAN 中断全关**，再跑——**复位依旧 ~3.3s**。
- **结论**：复位跟中断无关，**就是读 0x1B0 地址**本身触发总线错误。这条证伪很值：它把排查方向从"中断"收敛到"地址访问"，一步到位指向邮箱寄存器缺失。
- **教训**：**一个假设要用"最小干预"证伪**——关掉可能的元凶（中断），现象不变，就直接排除它，别在错误方向耗时间。

### 坑 12：过滤器寄存器读取不稳定——同一份写代码，两次启动读到完全不同的值

- **数据**（同一位时序、同一份直写过滤器代码，两次上电）：
  - 第 1 次：`fa0=1 fmr=81664(0x13F00) fm1=1 fs1=1 ffa=0 fr1=0 fr2=2242430(0x22377E)`——写入基本生效
  - 第 2 次：`fa0=0 fmr=15697(0x3D51) fm1=17551(0x448F) fs1=74188(0x121CC) ffa=35249(0x89B1) fr1=2201216(0x2194A0) fr2=2242430(0x22377E)`——**全部垃圾值**
- **解读**：过滤器块（0x200~0x244）在这颗克隆上**读写都不稳定**；而 `fr2@0x244` 在**每一次运行都恒读 0x22377E**（写什么都不理）——是块只读的固定内容，不是我们的掩码。这解释了为什么 HAL ConfigFilter 偶发"生效/不生效"、为什么 fmp0 一会儿 3 一会儿 0。
- **教训**：**寄存器"写进去"不等于"读得到"，更不等于"行为符合语义"**。克隆芯片上寄存器回读是判断外设真实性的第一道照妖镜：写-读-回读一致才算数，回读垃圾 = 外围的寄存器块没实现或实现错误。

### 坑 13：IER 写不进去 + hcan.State 读到 255——连软件状态都不可信

- **数据**：`IER` 写 2 读回 `0x40750B`、写 0 读回 `0x783800`——**写什么都不对，读回全垃圾**；`hcan.State`（RAM 变量）读到 **255**（非法值，合法枚举只有 0~5）。
- **解读**：IER 寄存器写不进去说明这颗克隆的 CAN 中断控制路径也是坏的/不标准的；`hcan.State=255` 意味着连 HAL 句柄的 RAM 状态都被破坏或读到异常。这俩和坑 9/12 连起来，**整块 CAN 外设除了发送路径，其余全是坏的**。
- **教训**：判断外设健康度不要只看一个寄存器，要看**整组寄存器能否 round-trip**（写-读一致）+ 句柄状态是否合法。多个独立坏点同时指向同一外设 = 外设本体问题，不是配置问题。

### 坑 14：fmp0=3 幻影——RF0R 读到的 FMP 与 HAL 排空时读到的不一致

- **现象**：DBG 里 `fmp0=3 full=0 ovr=1`（FIFO0 说有三帧待取、且溢出过），但 HAL 的 `GetRxMessage` 在中断回调里**永远排不空**（rx 计数恒 0）。
- **分析**：HAL_CAN_GetRxMessage 逻辑可证明：当 `State=LISTENING(st=2)` 且 `FMP0≥1` 时**必然返回 HAL_OK 并读出帧**。既然代码没走错路径，唯一解释是 **RF0R 寄存器本身不稳定**——DBG 读到 3，中断里读到 0，同一寄存器不同时刻"变"。
- **教训**：**"寄存器读值"在克隆上不是稳定事实**。当软件逻辑可证明正确但现象矛盾时，怀疑寄存器读取本身。这也是为什么这颗芯片上基于"读状态→再操作"的一切 HAL 流程都不可靠。

### 坑 15：同一固件板 B 好、板 A 坏 = 硅片问题判别法 ★

- **数据**：从站固件（V9_CAN-副本，干净 HAL ConfigFilter + 中断 + GetRxMessage）烧到 **板 B**：PC13 每帧闪、自动 ACK 板A 的 0x101——**完全正常**。同一份 CAN 初始化/回调代码路径在 **板 A**：从未收到一帧。
- **解读**：这是**最有力的对照**——软件栈完全一样，唯一变量是硬件。板 B 证明这套 HAL 流程是对的；板 A 用同一套流程失败，**问题在板 A 的硅片，不在软件**。
- **叠加证据**：`DBGMCU->IDCODE @ 0xE0042000` 读 **0**（正品 F103 应读 0x410/0x411 之类），丝印却是"STM32F103C8T6"——**假丝印 + 假 ID**。
- **教训**：**排障到"软件侧无懈可击"时，一定要做跨板对照实验**。"同一固件在一块板好、另一块板坏"直接锁定硬件，避免在错误方向上无限改软件。芯片真假用 chipid + 寄存器回读双重验证。

### 坑 16：换板决策——板 A 判死出局，焊死的板 C 照样能测

- **判定**：板A 的 CAN **任何角色都不行**——主站要收反馈、从站要收目标，**都要 RX**，而 RX 因 0x1B0 缺失物理不可能。6 版固件（HAL 过滤器/无过滤器/GD32 直写/裸排空/关中断/只读 RF0R）全部验证同一结论，不再浪费迭代。
- **板A 的剩余价值**：电机/编码器/串口/OLED/PID **全正常**（CSV 流证明），仍是一块完整单机伺服板，退居"单节点电机演示"，不浪费。
- **板 C 物理问题**：剩下的板子引脚是**焊死的（朝上），进不了面包板**。解法：**引脚朝上反而好接——用母对母杜邦线从板 C 的引脚跳出来**，接 ST-Link（PA13/PA14/GND）、接收发器（PB8/PB9/3V3/GND）、接 CH340（PA9/PA10/GND）。焊死完全不影响测试。
- **教训**：**该换板就换板**，不要在已知死路上耗迭代；而"板子进不了面包板"从来不是障碍——杜邦线是通用的。

### 坑 17：换板后一次通过——干净主站 + 兼容过滤器 + 双 LED 判据

- **动作**：重建干净主站 `V9_CAN_master`（从干净从站 V9_CAN-副本 复制，`NODE_ID 0`，4 处改动：NODE_ID、主站过滤器改精确匹配 0x201 mask=0、串口 CAN DBG 行、主站收帧闪 PC13）。
- **结果**：板 C 烧主站固件、板 B 保持从站固件组网——**两块板 PC13 均匀快速闪**（板 C 收 0x201、板 B 收 0x101），双向链路成立。故障注入（拔总线线→双板停闪，板 B 5s 后快闪 5 下报警→插回自动重传恢复）与看门狗浸泡（5 分钟不复位）**全部通过**。
- **教训**：**换板的前提是把"判据"想清楚**（双 LED 闪 = 链路活、复位周期 = 卡死指纹、DBG 计数器 = 计数级证据），这样换板测试一次就能定性，不用猜。

## C. 一句话总结

CAN 双板联调的坑分三层：**物理层的坑**（250kbps 极限、终端电阻、共地、收发器 3V3）、**协议层的坑**（过滤器掩码 STM32/GD32 语义相反、自由文本行保串口协议）、**芯片真实性的坑**（克隆只实现发送路径，读邮箱就总线错误，寄存器回读全垃圾——这是本阶段最深的坑，也是最有价值的面试素材）。最值得记住的排查方法两条：**对照实验**（同一固件板 B 好板 A 坏 = 硅片问题，删掉某段代码故障消失 = 那段代码的问题）和**时序指纹**（~3.3s 复位周期 = 2s 调试周期 + 1s 看门狗 + 启动时间，反推卡死点）。最终换板一次通过，链路打通。

### 坑 18：从站编码器"读数恒 0"——先查硬件，别先怀疑代码 ★

- **现象**：从站（板B）电机#2 能转，但串口 CSV 的 `enc` 列恒 0（或 0/1 抖动），位置环永不收敛 → 全速追 → 堵转保护杀停。"先转很多、后不转"的完整机制。
- **排障关键**：怀疑代码前，先把从站固件的编码器路径和**已知正常的主站固件逐字节对照**：`MX_TIM2_Init`（编码器模式 TI12、Prescaler=0、Period=65535）、`HAL_TIM_Encoder_MspInit`（PA0/PA1 输入+上拉）、`HAL_TIM_Encoder_Start(TIM_CHANNEL_ALL)`、无 TIM2 重映射、TIM2 时钟使能——**两边完全相同**。同一份代码一块板读数、一块板恒 0 → **差异必在硬件**。
- **硬件排查顺序**（用万用表，按概率）：
  1. **测编码器供电**：蓝↔黑 应有 ~3.3V。0V = 蓝没接 3V3 / 黑没接 GND / 插头错位没落上。
  2. **测 A/B 信号**：转电机，绿↔黑、黄↔黑 应看到 0↔3.3V 翻转。不动 = 模块没输出。
  3. **换编码器对照**：把正常板的编码器插头拔到故障板 → 能数 = 原编码器/接线坏。
- **⚠️ 供电接反（蓝→GND、黑→3V3）会直接烧霍尔传感器**——烧了就永久死，只能换模块。
- **教训**：**"代码是不是错了"要用对照实验回答，而不是猜**。同源固件一块板好一块板坏，物理变量差异 > 代码变量差异，先排硬件。本次结论：编码器路径代码没问题，是板 B 编码器硬件问题（重新接线后正常）。

### 坑 19：分布式里"谁拥有目标"——从站本地命令会被主站广播覆盖

- **现象**：从站串口发 `pos -200`，CSV 的 target 只闪一拍 `-200` 就被 `200` 盖回——主站每 100ms 广播它自己的目标（默认 200），从站的 `g_target_position = g_remote_pos` 每帧跟随。
- **解读**：**这是设计行为，不是 bug**。在分布式架构里，从站的目标永远由主站 CAN 决定，本地串口命令只是"单机调试口"。要驱动从站电机，**命令必须发给主站**。
- **判据**：从站 target 列 = 主站广播值且不复跳 → 下行链路通；从站 enc 收敛到 target → 闭环通。这两条看 CSV 一眼确认。
- **教训**：分布式调试先想清楚"目标的唯一来源"，不然会被"为什么命令没生效"带偏。

### 坑 20：堵转保护依赖编码器反馈——编码器坏了会"假堵转"

- **机制**：DiagTask 判定 `pwm != 0 && speed≈0` 持续 1s → `g_stall=1` → ControlTask 清 PWM 杀停。**speed 来自编码器**——编码器不读数时，位置环还在全速追（pwm=49），但速度永远算 0 → 堵转误触发。
- **表现**："上电转很多 → 停死"，和真堵转无法从外部区分。排障顺序：先确认编码器在读数（坑 18），再谈堵转。
- **教训**：**保护逻辑的输入坏了，保护逻辑会误报**。堵转检测的健全性依赖反馈链路的健全性。

### 坑 21：主站"能往前不能往后"——反向脚接触不良的症状特征

- **现象**：主站 `pos 1000` 超调到 1054（误差 -54），反向 PWM 一路加到 **-48**，编码器 2 秒纹丝不动 → 堵转锁死在 1054。正向（198→506→1054）完全正常。
- **定位**：TB6612 反向驱动 = AIN1=L、AIN2=H。**若 AIN2（PB1）悬空/接触不良**：正向（AIN1=H、AIN2=L→浮空读低）还能转，反向（AIN1=L、AIN2=H→浮空带不动）直接废——症状"能往前不能往后"完全吻合。重新接线后消失。
- **教训**：位置环超调修正**依赖反向驱动**，反向脚接不好只表现为"往回调不动"——这不是 PID 问题，是方向驱动硬件问题。验证：从高位 `pos 0`，走不回来就是反向断了。

### 坑 22：CAN 三种故障指纹——"全死" / "时通时断" / "复位循环" ★

- **全死（本次）**：主站 `CAN DBG rx= 15 tx= 18` 两个计数器**冻结**。tx 冻结 = 帧没人 ACK（邮箱一直重传）、rx 冻结 = 收不到反馈 → **从站不在总线上**。本次诱因：给板 C 加 OLED 时，**OLED 在 PB6/PB7、CAN 在 PB8/PB9，引脚相邻**，跳线碰/挤了收发器那几根线。
- **时通时断（阶段三踩过）**：rx=tx 有时涨有时停 → 接触不良（插头虚接）。
- **复位循环（板 A 那种）**：横幅每 ~3.3s 重打 → 芯片级硬故障。
- **判别**：**看计数器冻结还是周期复位**。冻结查总线物理（从站上电？收发器排线？相邻引脚短路？终端/共地）；复位循环查固件/芯片。
- **教训**：**加新硬件时检查引脚邻接**——PB6/PB7 与 PB8/PB9 只差两根脚位，杜邦线一歪就串。

### 坑 23：OLED 双板布局——从站反馈从 0x201 载荷提取

- **主站改动**（V9_CAN_master）：RX 回调主站分支原来只闪 PC13、不存数据；新增把 `0x201` 载荷 [0:1] 位置 + [2] status 锁存到 `g_slave_pos`/`g_slave_stall`。DisplayTask 布局改成 `M-POS/M-TGT/M-SPD/M-PWM/S-POS`，第 5 行显示从站位置，从站堵转时显示 `STALL`。
- **验收判据**：OLED 上 `M-POS` 和 `S-POS` 同步跟踪主站目标、`CAN OK <count>` 递增 = 双板位置同屏 + 链路活。
- **教训**：主站的"数据面"从阶段三的"只闪灯"升级到"存从站反馈"，是分布式系统显示层的自然延伸——反馈链路通了，显示就只差把数据取出来。

### 坑 24：CAN 清堵转标志（协议 bit1）——让主站能远程解锁从站

- **背景**：从站 `g_stall` 只有本地串口 `pos` 或断电能解锁。演示时从站一堵转就死锁到断电，不可接受。
- **实现**：主站串口收到 `pos` 命令 → `g_clr_stall_cnt=10`（CANTask 在接下来 ~1s 的 0x101 帧里 flags 带 bit1=0x02）→ 从站 RX 回调 `if (rx_data[2] & 0x02) g_stall = 0;`。
- **验证**：捏住从站电机 → OLED `S-POS` 变 `STALL` → 松手主站发 `pos 500` → 从站自动解锁恢复，免断电。
- **教训**：**协议预留的标志位是给"运维通道"留的**——阶段三设计协议时预留 bit1，5.3 才用上。设计时"宁可多留不用，不要用到再扩"。
